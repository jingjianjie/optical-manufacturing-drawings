# 中文与工程符号

## 分开定位四个问题

1. **文字内容**：回读得到的 Unicode 是否是原文？检查 TEXT/MTEXT、ATTRIB/ATTDEF、块定义及标注的文字替代。读取出乱码是编码问题，换字体不会修复；避免用 `errors=ignore` 丢字符。R2007+ DXF 通常为 UTF-8，较旧版本依代码页及 Unicode 转义存储，让库按文件版本处理，不对整个 DXF 做猜测转码。
2. **字体引用**：检查 STYLE 的 font/bigfont、实体 style、MTEXT `\f...;`/`\F...;` 内嵌覆盖。STYLE 改了仍可能被内嵌字体盖掉。嵌套块中的文字同样要检查。
3. **字形覆盖**：用 `font-check` 检查实际图纸字符。`.ttc` 有多个 face，逐 face 看结果；集合中某个 face 覆盖并不代表 CAD/渲染器选择了该 face。SHX 与 bigfont 不是 TTF，fontTools 无法证明其覆盖；用目标 CAD 实测或选择经核实的替代。
4. **排版与呈现**：字体引擎、替代字体、宽度因子、段落与行距会改变外观。检查最终文件的渲染，尤其窄单元格、混排符号、叠式分数与公差。字形存在仍可能被渲染器选错。

## 常见诊断分支

- ezdxf 1.4.5 写 R2000/ANSI_1252 后，本次回读的中文文字与图层名仍是字面 `\U+xxxx`；ACadSharp 也可能继续透传，导致“写前=写后”的字符串比较通过，而渲染显示转义码。这不是缺字体。已验证的路径：`unicode-copy` 解码到现代 UTF-8 DXF → ACadSharp 写 DWG → 回读 DXF → 渲染中文正常。脚本处理 CRLF 文本时使用 universal-newline StringIO，否则 DXF 节名称尾部的 CR 会破坏解析。

- TTC face选择可能造成字形异常，建议用实际渲染验证；需要时试用单字体文件，不根据一次结果对整个字体家族作结论。
- 覆盖汉字和Δ不等于覆盖Ø、⌀、上下标等工程符号。按实际字体文件检查全部字符，避免凭字体名判断。
- 若出现 `skipping MTEXT ... not enough space`，该预览漏画了对象，即使进程退出码是 0。先定位文字框宽度/格式/字体，只有在允许重排的输出中调整。原文字仍在 DXF 中不代表交付预览完整。

## 字体选择与修复

保真任务优先使用原字体。新增中文模板可选本地可用的 CJK TTF/OTF；选定后运行实际字符覆盖检查，再渲染。字体文件用可解析的名称，并交付所用 family/文件名与安装前提。不要把 Windows 字体复制进 skill 或分发包；使用许可明确的字体时按其许可处理。

混合工程符号可选覆盖整个字符集的字体，或给特定文字 run/实体指定已验证的符号字体；不要依赖隐式 fallback。需要内嵌字体 run 时验证目标 CAD 和预览端都能解析。工具无法表达所需混排时，保持原文并明确缺字，不能把 Ø 改成 φ、把 Δ 改成 △ 来消除告警。

`%%d`、`%%p`、`%%c` 和 Unicode 工程符号的原始表示要留在审查记录中。glyph-check 使用库解码的可见文本做候选筛选，同时 inspect 保存原文字和格式码。MTEXT 的 `\S`、上下标、字号、粗斜体及段落格式不能无条件 `plain_text()` 后回写；仅用户要求生成统一样式的空白模板时，可在已审查范围重建。

在副本局部设字体的最小示例：

```python
doc.styles.new('CN_Checked', dxfattribs={'font': 'chosen-font.ttf'})
for entity in selected_text_entities:
    entity.dxf.style = 'CN_Checked'
    # MTEXT 内嵌字体另行逐段处理，保留其他格式；这里不自动 strip。
```

不要通过 matplotlib 全局 `rcParams` 证明 CAD 字体已修复：它不等于 CAD 文本 STYLE 的字体解析。字体调整后，重新打开输出并生成预览。

## 字体验收

报告原文、样式/内嵌字体、候选字体文件与 face、缺失字符码点。新增模板至少放大检查一处中文栏目、一处指标符号和最长文本行；多种文字样式分别抽查。交付 DWG 时以 DWG 回读或原生 CAD 的预览为准；仅看写入前 DXF 不足以证明转换后外观。
